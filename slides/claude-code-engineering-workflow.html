Model / effort policy

モデルは「強い順」ではなく「役割」で選ぶ

下限は Sonnet

Haiku は使わず、日常の調査・実装・軽いレビューは Sonnet を基本にする。

判断は Opus

設計、ルール検証、複数repo横断、難しいレビューでは Opus high〜xhigh を使う。

Opus highOpus xhigh

慎重な操作検証優先

安定性重視の切替

モデル固定フェーズ境界で切替

性能が高いモデルは、必要と判断すれば sub agent への委譲を自動で選ぶことがあるため、普段は「必ずsub agentを使え」とは書かず、広い探索や隔離したい調査だけ明示します。

High-performance model policy

高性能モデルには「進め方」も任せる

細かい手順より成果を渡す

Opus などの高性能モデルには、Plan mode・sub agent・並列調査まで細かく指定しすぎず、まず 目的・制約・完了条件 を明確に渡す。

OutcomeConstraintsDone criteria

オーケストレーションを委譲

必要ならモデル自身に、調査、Plan、sub agent、並列化、検証の進め方を選ばせる。人間は成果物とリスクをレビューする。

必要時Plan必要時Subagent必要時並列化

小さい仕事は落とす

一方で、明確で局所的な修正やテスト追加は Sonnet で十分。高性能モデルを常用して過剰な推論コストを払わない。

局所修正小さなPR

レビューは独立させる

高性能モデルに任せた作業ほど、計画書やdiffを 別セッション でレビューする。観点を渡さないレビューも、想定外の指摘を得るために有効。

fresh contextOpus xhighあえてSonnet

例：「この3リポジトリを調査し、共通ルールとrepo固有ルールを整理して。必要ならsub agentを使い、根拠つきで改善案を出して。」のように、手順ではなく達成状態を渡す。

Context control

main context は「量」より「質」

/clear

タスク境界で使う。設計済みの PLAN.md や SPEC.md を残して、fresh context から実装する。

例：テスト基盤の設計後に /clear → Sonnetで実装

/compact

同じ流れを継続するときに使う。採用済み設計、変更ファイル、残タスク、検証コマンドだけ残す。

例：debug中にcontextが肥大したが、まだ作業を継続したい

私の運用： context は使用率ではなく 情報密度 で管理する。古い試行錯誤、却下案、関係ないgrep結果、解決済みエラーが残るなら、使用率が低くても質が悪い。

compactは容量閾値ではなく、調査完了 → 設計、設計確定 → 実装、実装 → debug のようなフェーズ境界で行う。使用率が高くても、現在の判断に必要な情報だけなら機械的にcompactしない。

Sub agent policy

Sub agent は「要約器」ではなく「調査員」

使う場面

repo全体の検索、既存パターン調査、影響範囲の洗い出しなど、広く浅い探索を任せる。

戻してほしい情報

結論だけではなく、判断に影響する事項と 根拠ファイル・該当箇所 を返してもらう。

Main の役割

sub agent の報告を鵜呑みにせず、重要な前提だけ main が一次情報を再確認する。

使わない場面

数ファイルの確認、設計判断に直結するコード読解、局所的な修正は main で直接読む。

判断基準は「context使用率」ではなく、探索過程そのものをmainが知る必要があるか。

Parallel research

独立した調査は並列 sub agent に分ける

良い使い方

複数repo、複数領域、複数観点のように、互いに依存しない調査を別々のsub agentへ並列に任せる。

Repo ARepo BRepo C

具体例

開発ルール検証では、各repoの CLAUDE.md / CI / lint / test / Git運用 を同じ形式で調査させ、mainで横断比較する。

返却フォーマット

発見事項、根拠ファイル、repo固有の制約、横断適用できそうなルール、追加確認事項を揃えて返してもらう。

使いすぎない

数ファイルを読むだけ、前の調査結果に次が依存する作業、同じ流れを縦に追う作業は main か逐次調査で十分。

判断基準：ファイル数ではなく、調査を独立した塊に分割できるか。並列化は速いが総tokenは増えるため、mainは統合・比較・意思決定に集中させる。

Review strategy

計画書も実装結果も別セッションでレビュー

計画書レビュー

複雑な作業では、実装前に PLAN.md / SPEC.md を別セッションの高性能モデルでレビューさせる。

Opus xhigh前提確認

実装後レビュー

設計判断、大きな導入、複数ファイル変更の後は、別セッションで Opus xhigh に深くレビューさせる。

fresh sessiondiff中心

あえて Sonnet レビュー

下位モデルの Sonnet に、過剰設計・読みにくさ・単純な見落としを拾わせることもある。

Sonnet high素朴な視点

観点ありレビュー

「正しさ」「テスト妥当性」「CIコスト」「ルール化しすぎていないか」など、狙って見てほしい観点を渡す。

観点なしレビュー

あえてレビュー観点を渡さず、モデル自身に違和感・リスク・見落としを自由に拾わせる場合も有効。

複雑な作業ほど Planner / Writer / Reviewer を分ける。計画書は前提・影響範囲・分割方針を、実装後はdiff・テスト・運用リスクを中心に見る。

Continuous improvement

Harness も公式情報で定期更新する

固定しない

Claude Code は model / effort / sub agent / compact / skills / hooks の推奨やコスト感が変わるため、Harness は一度作って終わりにしない。

見る情報

公式 docs、best practices、model config、subagents、skills、hooks、costs、CHANGELOG を定期的に確認する。

更新は差分ベース

最新情報をそのまま反映せず、現在の Harness と公式情報の差分だけを抽出して、変更理由・期待効果・根拠を確認する。

代表タスクで検証

フロントエンドテスト基盤、ルール検証、AI開発プロセス構築の3パターンで、正確性・速度・token効率が改善するかを見る。

運用：公式情報チェック → 影響箇所の抽出 → Harness変更案 → diffレビュー → 代表タスクで検証 → 採用、の順で更新する。

原則は安定させる。変えるのは Claude Code 依存の戦術、たとえば model / effort / sub agent の使い方、compact方針、skills / hooks の活用方法。
