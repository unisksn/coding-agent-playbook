Claude Code 用の `code-review-loop` スキルと、それが利用する専用サブエージェントを作成してください。

目的は、修正担当とは別のサブエージェントによるコードレビューと修正を交互に繰り返し、指定回数以内で指摘の解消を目指すことです。
親エージェントは進行管理だけを担当し、レビューと修正は専用サブエージェントへ委任します。
以下の仕様を実装してください。

## 呼び出しと引数

- `/code-review-loop [対象] [x=3] [y=2]`
- x：Sonnet による修正担当の最大実行回数。デフォルトは 3。正の整数。
- y：Opus による追加修正担当の最大実行回数。デフォルトは 2。0 以上の整数。
- 引数は空白区切り。`x=N` / `y=N` 形式は回数、残りの先頭トークンが対象、その後ろに整数が続けば順に x、y。
- 対象の解釈
  - 指定なし：現在のブランチの変更（コミット済みと未コミットの両方）。
  - 裸の整数、`#N`、PR の URL：PR。回数だけ変えるときは `x=` / `y=` 形式を使う前提にする。
  - それ以外：比較元ブランチまたは ref（検証に失敗したら停止）。
- スキルは多数のサブエージェントを起動しコードを書き換えるため、ユーザーの明示的な呼び出し専用にする
  （`disable-model-invocation: true`）。

## 対象の確定と開始時の表示

開始時に比較元のコミットIDと対象範囲を確定し、ループ中は変更しない。対象範囲は常に
「比較元コミット → 現在の作業ツリー（HEAD + 未コミット + 未追跡）」とし、ループ中の修正で
追加・変更されたファイルも範囲に含める。元の差分だけに限定しない。

- 指定なし：比較元ブランチを次の順で決める。(1) 現在のブランチに開いた PR があればその base ブランチ、
  (2) リポジトリの既定ブランチ、(3) 取れなければ停止して確認。比較元 = `origin/<比較元ブランチ>` との
  merge-base。比較元が HEAD と一致する場合は HEAD を比較元にして未コミット差分だけを対象にし、
  コミット済みも未コミットも差分がなければ停止して対象を確認する。
- PR：PR の base ブランチとの merge-base。現在のブランチが PR の head でない、または HEAD が PR の
  head コミットを含まない場合は、checkout せずに停止して報告する。
- ブランチ/ref：そのブランチとの merge-base。

未コミット差分がある場合は、ステージ済み・未ステージ・対象となる未追跡ファイルを確認し、開始時点の
未コミット差分と未追跡ファイル一覧を実行ディレクトリに退避する（ユーザーの既存変更の識別用。自動では
復元しない）。修正担当には、既存変更を破棄する操作（checkout / restore / stash / reset / clean）を禁止する。

実行ディレクトリ（例：`~/.claude/tmp/code-review-loop/<日時>-<repo>/`）に、対象・比較元コミットID・
x/y・仕様（PR のタイトルと本文、比較元からのコミットメッセージ、呼び出し時にユーザーが添えた説明）・
リポジトリの指示ファイルのパス・既知の検証コマンドをまとめた context ファイルを置き、各サブエージェントに
パスで渡す（差分本文はプロンプトに貼らない）。

開始時に以下を短く表示する。値は固定の例ではなく、実際の引数とサブエージェントの設定ファイルから取得する。

- 対象と対象範囲
- 比較元（ブランチ名または HEAD と、確定したコミットID）
- x、y
- 各役割に設定されたモデルと effort の表

## モデル構成

以下の専用サブエージェントを `code-review-loop-*` の名前で定義し、モデルと effort を frontmatter の
`model` / `effort` に実際に設定する。本文の指示だけで代用しない。

| 役割 | agent 名 | モデル | effort |
|---|---|---|---|
| 初回レビュー | code-review-loop-review-initial | Opus 5.5 | high |
| 2回目以降のレビュー | code-review-loop-review-followup | Opus 5.5 | medium |
| 通常修正 | code-review-loop-fix-sonnet | Sonnet 5.5 | medium |
| 追加修正 | code-review-loop-fix-opus | Opus 5.5 | medium |

- 初回レビュー用と再レビュー用は別のサブエージェントとして定義する。
- モデルはバージョンを固定する。alias（`sonnet` / `opus`）ではなく完全なモデルIDを使う。利用環境に対応する
  正確なモデルIDと frontmatter の指定方法を公式ドキュメントで確認すること。
- レビュー担当は読み取り専用にする（ツールを Read / Grep / Glob / Bash に限定し、`permissionMode: plan`）。
  レビュー結果は親が実行ディレクトリに保存する。修正担当は自分の報告を実行ディレクトリに書く。
- スキル起動時に 4 つのサブエージェントの frontmatter（model / effort）を実測し、スキル内の契約表と
  1つでも異なる、またはファイルが欠けていれば、黙って代替せず理由を報告して開始前に停止する。
- 各サブエージェントは出力の先頭に、自身のシステムプロンプトに記載された exact model ID を
  `model:` 行で自己申告する。親はこれを契約と照合し、不一致（fallback や alias 解決による差し替えを含む）
  なら理由を報告して停止する。effort は実行時に自己申告する手段がないため frontmatter の確認のみとし、
  最終報告でその旨を明記する。
- 親は Agent tool に `model` パラメータを渡さない（frontmatter の設定で起動させる）。
- レビューと修正を同時に実行しない。各レビュー・各修正は新しいサブエージェントで実行する。

## 回数の定義

x、y はレビュー回数ではなく、修正担当の実行回数を表す。

- 初回レビューは修正回数に含めない。
- 修正担当を実行したら、コード変更の有無にかかわらず 1 回と数える。誤指摘への反論だけを返した場合も 1 回。
- 修正担当の各実行後に、必ず再レビューを実施する。ただし、修正担当が実行不能または要判断を返した場合は、
  再レビューせずにその状態を報告して停止する。
- 前回の再レビュー結果を次の修正担当へ渡す。同じコード状態へのレビューを重複実行しない。
- 修正回数（Sonnet / Opus 別）とレビュー回数（初回 high / 以降 medium）を別々に記録する。
- 上限を自動で増やさず、回数をリセットしない。

通常の上限は、修正担当が x+y 回、レビューが初回を含め x+y+1 回となる。
ただし、レビュー未完了時の再実行（後述、各レビューにつき 1 回まで）もレビュー回数に数えるため、
レビュー回数はこの上限を超えることがある。修正担当の上限 x+y は再実行の有無にかかわらず変わらない。

## 処理の順序

1. Opus 5.5 / high で初回レビューを実施する。
2. レビューが完了し、対象指摘が 0 件なら終了する。
3. 対象指摘がある場合、Sonnet 5.5 / medium で修正と検証を実施する。
4. 修正担当の実行後、Opus 5.5 / medium で再レビューする。
5. 対象指摘が残る限り、Sonnet による修正担当の実行を最大 x 回まで繰り返す。
6. x 回実行後の再レビューでも対象指摘が残る場合、修正担当を Opus 5.5 / medium に切り替える。
7. Opus による修正と Opus 5.5 / medium による再レビューを最大 y 回まで繰り返す。
8. 最後の修正後も必ず再レビューする。
9. 最終レビューでも対象指摘が残る場合は「上限到達・未解決」で終了する。

y=0 の場合、Sonnet の最終修正後の再レビューで対象指摘が残っていれば終了する。
担当や段階が切り替わっても、初回レビューをやり直したり、レビューの effort を high に戻したりしない。

## 指摘対象の切り替え

x 回目の修正担当へ渡す指摘を生成するレビューから、マージをブロックする問題だけを対象とする。
レビュー番号を r（r=0 が初回、r=k が修正 k 後の再レビュー）とすると、`r >= x-1` でブロッキングのみ。

- x=1：初回レビューからブロッキング問題だけを対象とする。
- x>1：初回レビューと、修正 1〜修正 x−2 の後の再レビューでは、根拠のある実質的な問題全般を対象とする。
  修正 x−1 の後の再レビューから最後まで、ブロッキング問題だけを対象とする。
- 切り替え回のレビューでは、過去の未解決指摘を再分類し、非ブロッキング指摘を「対象外」として
  修正キューから外す。切り替え以降、非ブロッキング指摘を新たに報告・修正しない。
- レビューが完了し、再分類後の対象指摘が 0 件なら終了する。

ブロッキング問題とは、そのままマージすると具体的な不具合、仕様違反、セキュリティ問題、データ破損・
漏えい、重大な性能問題、必須チェックの失敗などにつながる問題を指す。好みの命名、軽微な読みやすさ、
任意のリファクタリング、根拠のない将来懸念はブロッキング扱いにしない。ただし、リポジトリの必須ルールは
確認する。

デフォルトの x=3、y=2 では以下の順序になる。

| 手順 | 担当 | レビューの指摘対象 |
|---|---|---|
| 初回レビュー | Opus 5.5 / high | 実質的な問題全般 |
| Sonnet 修正 1 → 再レビュー | Sonnet 5.5 / medium → Opus 5.5 / medium | 実質的な問題全般 |
| Sonnet 修正 2 → 再レビュー | 同上 | ブロッキング問題のみ（切り替え・再分類） |
| Sonnet 修正 3 → 再レビュー | 同上 | ブロッキング問題のみ |
| Opus 追加修正 1 → 再レビュー | Opus 5.5 / medium → Opus 5.5 / medium | ブロッキング問題のみ |
| Opus 追加修正 2 → 再レビュー | 同上 | ブロッキング問題のみ |

各レビューで対象指摘がなくなれば、その時点で終了する。

## レビューの進め方

- レビュー担当はコードを変更しない。
- 対象差分、比較元、仕様、関連コード、修正担当の検証結果、過去の指摘と対応状況、現在の指摘対象の基準を渡す。
- 前回の指摘を修正担当の報告を鵜呑みにせずコードで検証しつつ、修正による回帰を含めて対象差分全体を
  レビューする。
- 指摘には、ID（全レビューを通じて連番で安定させる）、場所、問題、発生条件、具体的な影響、ブロッキング判定と
  その理由を付ける。
- 指摘数のノルマを設けず、問題がなければ「対象指摘なし」と返す。
- 指摘の状態を、解決済み・未解決・根拠付き却下・対象外として管理し、ID ごとの状態遷移の履歴
  （レビュー回ごとの状態と修正回ごとの対応：修正 / 反論 / 未対応）を一覧に残す。
- 修正担当が報告した検証の失敗や必須検証の未実施、指摘を消すためのテスト弱体化や必須チェックの無効化は、
  ブロッキング指摘として扱う。
- レビュー結果には、レビューが完了したか、未確認範囲や実行エラーがあるかを明記する。調査不足、実行エラー、
  必要な情報の不足でレビューを完了できなかった場合は、指摘 0 件でも「指摘なし」として成功終了しない。
  親は、原因が一時的な実行エラーなら同じ担当で 1 回だけ再実行（レビュー回数に数える）し、それでも
  未完了または情報・環境不足なら「実行不能」で停止する。

## 修正と検証

- 修正担当は指摘の妥当性をコードと仕様で確認し、妥当な問題を必要な範囲で修正する。
- 誤指摘の場合は、根拠を示して「反論」としレビュー担当の再確認に回す。修正担当の判断だけで解決扱いにしない。
- 関連するテスト、型チェック、lint などを実行する。回帰防止に必要なテストは追加する。指摘を消すために
  テストを弱めたり、必須チェックを無効化したりしない。
- 無関係な変更や、ユーザーの既存変更の破棄を避ける。共有環境への破壊的操作をしない。
- 修正内容、指摘ごとの対応、検証結果、未実施の検証を報告する。必須検証を実施できなかった場合や必須チェックが
  失敗している場合は、成功扱いにしない。
- 追加修正（Opus）は、残っている各指摘が解消しなかった原因（修正箇所の誤り、検証不足、反論と却下の
  繰り返し、仕様解釈の相違）を履歴から先に特定してから修正する。

## 指摘が往復した場合と停止条件

同じ指摘 ID について「修正→未解決」または「反論→未解決」が 2 回以上繰り返された場合、履歴から原因を確認する。

- 明確な実装不備なら、残り回数の範囲で修正を続ける。
- 仕様の矛盾、要求の曖昧さ、両立できない修正要求、レビュー担当と修正担当の仕様解釈の不一致など、人間の判断が
  必要な場合は「要判断」で停止し、判断事項・選択肢・影響を短く報告する。担当モデルの切り替えで仕様判断を
  押し切らない。
- 必要な情報や実行環境が不足し、安全に継続できない場合は「実行不能」で停止する。

## 終了時の報告

冒頭に次を短くまとめる。

- 結果：対象指摘なし／ブロッキング指摘なし／上限到達・未解決／実行不能／要判断
- 修正回数：Sonnet n/x 回、Opus n/y 回
- レビュー回数：初回 high n 回、以降 medium n 回
- 主な修正と検証結果（失敗・未実施の必須検証は結果と区別して明記）
- 残っているブロッキング問題
- 未確認範囲、未実施の必須検証、人間の判断が必要な事項、effort が設定ファイルでの確認のみである旨
- 実行ディレクトリのパス

詳細な指摘履歴は折りたたんで記載する。ブロッキング限定へ切り替えた後に成功終了した場合は
「ブロッキング指摘なし」と表現し、すべての改善事項がなくなったとは報告しない。レビュー未完了や
必須検証の未実施・失敗がある場合は、成功終了とは区別して報告する。

コミット、push、PR コメント投稿、マージは、別途指示がない限り実行しない。

## 作成後の確認

以上を満たすスキルと専用サブエージェントを作成してください。作成後、次を確認して配置場所、呼び出し例、
確認結果を簡潔に示してください。

- frontmatter の構文と、起動時のモデル・effort 実測が契約表と一致すること
- 回数上限、x=1、y=0、指摘対象の切り替え、コード変更なしの回数計上、指摘の往復、レビュー未完了時の終了判定
  （x, y を変えた机上検証で可）
- 修正担当サブエージェントを 1 回だけテスト起動し、自己申告の `model:` 行が設定した完全なモデルIDと
  一致すること
