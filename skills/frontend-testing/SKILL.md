# フロントエンドのテスト方針

**このスキルは判断基準だけを扱う。** 具体的なバージョン・実行コマンド・そのプロダクト固有の
ハマりどころは、各リポジトリの `AGENTS.md` / `docs/` に書く(ここには書かない)。
ツール固有で実測した落とし穴(setup で落ちる、通しで実行すると落ちる、何を assert しても通る)は、
症状・原因・対処と確認した版をセットにして、リポジトリの docs か別のスキルに分けて残す。

## 大原則

> **その振る舞いを十分な信頼度で検証できる、いちばん速く・局所的で・安定したレイヤーに置く。**

テストピラミッドの比率を機械的に当てはめない。判断材料は
**リスク・実行速度・保守コスト・信頼度** の4つ。

上位レイヤー(component → E2E)にテストを足すときは、
**下位レイヤーでは検証できない統合リスクが何なのかを説明できること**を条件にする。
説明できないなら、そのテストは下位レイヤーに置き直すか、書かない。

## テストを書く前に

**いきなりテストファイルを作らない。** 次の順で進める。

1. 製品コードを読む
2. その依存を読む(ロジックが実際どこにあるか)
3. 既存のテストを読む
4. テストの設定・setup ファイルを読む
5. **観測できる振る舞いを列挙する**
6. リスクを分析する(壊れると何が起きるか)
7. どのレイヤーで見るか決める
8. **下位レイヤーに同じ検証が既に無いか調べる**
9. 最小限のテストを書く
10. テストを実行する
11. lint / typecheck を実行する
12. 不要な mock・抽象化・重複が無いか見直す

書く前に、この3つを説明できること。

- **何の振る舞いをテストするのか**
- **なぜこのレイヤーなのか**
- **どの回帰リスクを防ぐのか**

## どのレイヤーに置くか

| | 問い | Yes なら |
|---|---|---|
| **Q1** | UI フレームワークもブラウザも無しで検証できる純粋なロジックか | **unit** |
| **Q2** | コンポーネントを1つ〜少数 mount すれば十分か | **component** |
| **Q3** | routing / 認証 / バックエンド / ブラウザ / 複数画面を統合しないと意味がないか | **E2E** |
| **Q4** | 同じ振る舞いを下位レイヤーで既に十分検証しているか | **原則、足さない** |

Q4 の例外は、上位レイヤーにしか無いリスク(配線・統合・ブラウザ挙動・routing・認証・
バックエンド連携)を説明できるときだけ。

### サーバ側のテストもレイヤーの候補に入れる

**フロントの3層だけで考えない。** サーバが返すもの — 未ログイン時のリダイレクト、
権限による 403、API のレスポンス形 — は、**バックエンドの request spec の方が速くて安定する**。
E2E に持ち込まない。

### レイヤーごとの責務

**unit**: 純関数、フォーマッタ、バリデータ、ドメインロジック、composable、
store の局所的なロジック、状態遷移、境界値の計算。
見るもの = 入出力・境界値・不正入力・エラー処理・状態遷移・既知の不具合の再現条件。
**コンポーネントの DOM を unit test で無理に検証しない。**

**component**: props に対する表示、操作による変化、フォーム入力、emit、条件付き描画、
バリデーションメッセージ、store / router との境界、loading / success / error の状態。
**内部実装(private メソッド・内部 ref・computed の中身・CSS クラスの構造)ではなく、
ユーザーから観測できることを見る。**

**E2E**: 重要なユーザージャーニーとシステム境界の統合。ログイン、主要画面への遷移、
登録・編集・削除、重要なフォーム送信、認証/認可、実ブラウザでないと確認しづらい振る舞い。
**細かい入力パターンや大量の境界値を E2E に置かない。**

### 重複させない(典型例: 入力フォーム)

| 検証したいこと | 置く場所 |
|---|---|
| 書式・桁数などの入力ルール | **unit**(ルールが純粋な関数なら) |
| 値の変換規則そのもの | **unit** |
| 変換・ハンドラが画面に繋がっている**配線** | **component** |
| サーバのエラーがメッセージとして表示される | **component** |
| その画面に到達して一連の操作が通ること | **E2E** |

**同じ「不正な入力ならエラー」を3層で書かない。** ルールは unit、配線は component、と役割で切る。

## 共通のルール

### 実装ではなく振る舞いをテストする

リファクタしただけで大量に落ちるテストは実装に密着しすぎている。
「ユーザーに何が見えるか」「何を操作できるか」「操作すると何が起きるか」を見る。

`wrapper.vm` 等で内部実装へ直接アクセスするのを既定にしない。使うなら
「なぜ観測可能な出力から検証できないのか」を説明できるときだけ。

`mount` と `shallowMount` を機械的に統一しない。子まで含めた振る舞いが対象なら `mount`、
意図してコンポーネント境界を切りたいときだけ shallow / stub。

### 要素はユーザーが認識できるものから引く

component / E2E のどちらでも同じ優先順位を使う。

1. role(`getByRole`)
2. ラベル(`getByLabel`、ラベル文字列 → `for` → `id`)
3. 表示テキスト(`getByText`)
4. その他 user-facing なもの(placeholder、alt、title)
5. `data-testid` — ユーザー向け情報だけでは安定した selector を構成できないときの、
   **明示的なテスト契約**として

**避ける**: DOM 階層、`nth-child` / `findAll("input")[3]` のような添字、生成された CSS クラス、
壊れやすい CSS セレクタ、XPath。項目を1つ足しただけで壊れる。

### テストは単独で成立させる

実行順・他テストが残した状態・DB レコード・localStorage・sessionStorage・timer・
mock の状態に依存させない。

### 決定的にする

現在時刻・タイムゾーン・乱数・生成 ID・ネットワーク・アニメーション・非同期の順序を制御する。
**固定 sleep で解決しない。**

### 不具合修正には回帰テストを付ける

1. 不具合を再現する落ちるテストを書く → 2. **落ちることを確認する** →
3. 製品コードを直す → 4. 通ることを確認する。

**定義値やフラグを assert しただけのテストは実際の分岐を通っていないことがある。**
新規のテストでも、製品コードを一時的に壊して落ちることを確認する価値は高い
(壊す前に退避し、必ず戻して差分が空であることを確認する)。

## mock の方針

**mock は少ないほどよい。「unit test だから全部 mock」とは考えない。**
速くて・決定的で・副作用がなく・簡単に用意できる依存は**本物を使う**。

mock を検討してよい代表例:

- 外部 API / ネットワーク
- 時刻 / 乱数
- ブラウザ API、重い処理、制御できない副作用
- **失敗系を意図的に起こしたい依存**

逆に、ドメインモデル・フォームオブジェクト・store・UI フレームワークは原則そのまま使う。
**UI フレームワークを stub すると描画が消え、何を assert しても通るテストになる。**

**mock は自分が所有しない境界に置く。** API を差し替えるなら、自作の API クライアント
モジュールを `vi.mock` するより、ネットワーク境界(MSW 等のリクエストインターセプト)で
止める。クライアントの内部をリファクタしてもテストが壊れず、リクエストの形まで検証できる。
モジュール mock は「その境界を持つモジュールが1つしか無く、ネットワーク層まで再現する
コストが見合わない」ときに限る。

**テスト対象そのものを mock しない。** mock を置くときは
「なぜ本物ではだめなのか」を説明できること。mock の状態はテスト間で漏れないよう
clear / reset / restore する(設定で一括自動化できるならそうする)。

## 非同期の待ち方

固定時間の sleep で待たない。

- unit / component: `await`、`nextTick`、`flushPromises`、必要なら fake timers
- E2E: locator と web-first assertion の auto-wait に任せる。
  **`waitForTimeout()` を通常の同期手段として使わない**

## E2E 固有のルール

- **各テストを独立させる。** テスト A が作った状態をテスト B が使う構造にしない
- 前準備は fixture / API / 制御されたテストデータ / 認証状態で用意する。
  **多くのアプリにはテスト用のリセット API が既にある。まず探す**
- fixture / helper を使って、「何を検証しているか」が setup に埋もれないようにする
- **第三者サービスそのものを E2E で検証しない。** 必要なら境界を制御する
- **retry を flaky の放置に使わない。** retry でしか通らないテストは原因調査の対象
- 認証は毎回 UI からログインせず、保存した認証状態(storageState 等)を使い回す。
  ただし**ログイン導線自体を検証するテストは UI から行う**
- Page Object は単なる selector 置き場にしない。繰り返されるユーザー操作や
  ドメインの振る舞いを表現できるときだけ作る

### 導入順

最初から大量のシナリオを作らない。まず critical user journey を洗い出し、
**「壊れるとユーザーが主要機能を使えない」もの**から入れる。
happy path を E2E で守り、細かいバリデーションや edge case は unit / component に寄せる。

## snapshot

**既定の assertion にしない。** 特に巨大なコンポーネント HTML の snapshot は避ける
(何が仕様なのか読み取れず、変更のたびに無検証で更新されるため)。
安定した serialization や、構造全体を意図的に契約にしたいデータだけに使う。
**「簡単だから snapshot」で導入しない。**

## 抽象化とテストデータ

テストコードは製品コード以上に可読性を優先する。**setup / 操作 / 期待結果**がテストを
読むだけで分かる状態を保つ(Arrange / Act / Assert が識別できればよく、コメントを
機械的に付ける必要はない)。

**抽象化は必要になった時点で入れる。** helper / fixture / factory / builder / Page Object は、
同じ操作や setup が複数のテストで繰り返され、**ドメインの概念として名前を付ける価値が出た
時点**で切り出す。数件のテストのために大きな仕組みを作らない。1ファイル内で済むなら
spec の中に置いたままでよく、2つ目のファイルで同じことを書き始めたら共通化する。

**避けるもの**:

- 1回しか使わない helper
- 製品コードより理解しづらいテスト DSL
- すべてを隠す巨大なテストユーティリティ
- **assertion まで内部で行う不透明な helper**
- **各テストにとって重要な値を helper の奥に隠すこと**(何が効いている値なのかが
  テストを読んで分かること)

## テスト名

実装ではなく振る舞いを表す。既存の命名規則があればそれを優先する。

- 悪い: `calls handleSubmit` / `errorAttributes のテスト`
- 良い: `メールアドレスが不正なときにエラーを表示する`

## coverage

**カバレッジの数値をテスト品質として扱わない。**
「まだテストされていない重要なロジックを見つけるための補助指標」として使う。
数値を上げるためだけの意味の薄いテストを作らない。
**導入初期に既存コード全体を一気に高カバレッジにしようとしない。**

## 既存プロジェクトへの段階導入

テストがほぼ無い状態から、全面的な後追いテストはしない。
方針は **Leave the code better tested than you found it.**

1. 新しく追加するロジック
2. 不具合修正(回帰テスト)
3. 今回変更する既存コード
4. business critical な既存ロジック
5. 回帰リスクの高い箇所

## CI での実行区分

どのレイヤーをどこで回すかは、**フィードバック速度と信頼度の交換**として決める。
具体的なジョブ定義やしきい値はリポジトリ側に書く。

- **unit / component は毎 PR で全量。** 数分で終わる範囲を保つ。遅くなったら
  テストを減らすのではなく、E2E に置くべきでないものが混ざっていないかを疑う
- **E2E は PR では smoke(critical user journey の happy path)に絞り、全量は merge 後や
  定期実行に回す**。全量を PR の必須チェックにすると、flaky が開発全体を止める
- **必須チェックにするのは決定的なテストだけ。** flaky なテストは隔離して原因調査の
  対象にし、retry で通したまま必須チェックに残さない
- **E2E の前提(アプリ・DB・依存サービスの起動)は CI 側で用意し、テストランナーに
  二重で持たせない**

## 新しくテスト基盤を作るとき

- **将来必要になりそう、という理由で helper / factory / ディレクトリを大量に作らない。**
  いま必要な最小構成から始める
- setup ファイルに置くのは「無いと mount が落ちる」「無いと実行順に依存する」ものだけ。
  **足すときは、どのコンポーネントで何のエラーが出たかをコメントに残す**
- 製品のビルド設定(alias・拡張子の解決順)は再定義せず再利用する。
  書き写すと本番とテストで解決先がズレたときに気づけない
- **基盤を入れたら、実在するコンポーネントで loading / error / ダイアログ表示まで作って
  mount を通してから**規約を書く。軽いコンポーネントを1つ mount しただけでは足りない
  (jsdom に無いブラウザ API を UI ライブラリが参照するのは、ローディングやオーバーレイの
  状態を作ったときだけ、ということがある)。ドキュメントを先に書くと、動かない前提が正本になる

## レビュー時に見るもの

- 振る舞いをテストしているか。実装の詳細をテストしていないか
- レイヤーは適切か。他レイヤーと重複していないか
- test isolation が保たれているか
- 決定的か
- mock が過剰でないか。**テスト対象そのものを mock していないか。** 境界の位置は適切か
- 非同期の待ち方が適切か
- selector が壊れやすくないか
- **テスト名だけで意図が理解できるか**
- テストデータが理解しやすいか
- 抽象化が過剰でないか
- 製品コードのリファクタに不必要に弱くないか
- **実際に回帰リスクを減らしているか**
